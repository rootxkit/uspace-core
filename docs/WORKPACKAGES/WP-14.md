## The one rule of this release

Everything in C1 is **additive** under `docs/RELEASING.md` §1: new
functions, types, optional fields and constants; no change to what any
existing judgement returns for any input; no change to an exported
identifier's meaning; no vector file added, removed or edited. The tag
is `v1.1.0`, a minor. Concretely for every pull request of WP-14, WP-15
and WP-16:

- `git diff origin/main -- vectors/testdata/` is empty. The semver gate
  then prints `PASS - no file under vectors/testdata/*.json changed` and
  needs no CHANGELOG vector line, no lab pin and no label. A new vector
  file would be a **major** (`RELEASING.md` §3.2: "a new file counts as
  a behaviour change"), so none is written here even for the JWS helpers;
  §"Vectors" below says what goes to the lab instead.
- Every existing `TestVectors*` passes unchanged (`make vectors`), and
  every default of every `Config`/`Policy` keeps its value, so a system
  that upgrades without touching its configuration observes nothing new.
- No exported identifier of `v1.0.0` is renamed, removed or re-typed. A
  new field on an existing struct is zero-valued by default and the zero
  value means "as before".
- Counter names added here are stable from `v1.1.0` (E-09; CHANGELOG
  `[1.0.0]` "API declared stable" lists counter names as API).
- `go.mod` is unchanged: the JWS helpers use the `jws`, `jwk` and `jwa`
  packages of `lestrrat-go/jwx/v3 v3.3.0`, already required (plan §4).
  No new dependency, no cgo.

## What to build

All in package `auth`. Nothing below changes `Verifier`, `Issuer`,
`ReceiverVerifier` or their vectors.

### 1. `KeyRing`: the publisher's signing keys and its JWKS

```go
// SigningKey is one RSA private key under a kid.
type SigningKey struct{ KID string; Key *rsa.PrivateKey }
type KeyRing struct{...}                                           // safe for concurrent use
func NewKeyRing(active SigningKey, retired ...SigningKey) (*KeyRing, error)
func (r *KeyRing) Rotate(next SigningKey) error                    // next becomes active; the previous active joins retired
func (r *KeyRing) Retire(kid string) error                         // drops a retired key; refuses the active one
func (r *KeyRing) ActiveKID() string
func (r *KeyRing) KIDs() []string                                  // active first, then retired, stable order
func (r *KeyRing) JWKS() jwk.Set                                   // every key, public, kid, alg RS256, use sig
func (r *KeyRing) Issuer(iss string) (*Issuer, error)             // an Issuer on the active key (the authority's token service and its publication signer share one JWKS, M26)
```

Rules: the key checks are those of `NewIssuer` (non-nil, >= `MinRSABits`,
`Validate`, non-empty `kid`); a duplicate `kid` is a startup error (B-14).
Retired keys verify but never sign: that is the two-key overlap of cisp
Q16 (a verifier that has cached the old JWKS keeps verifying through a
rotation). `KeyRing` holds keys the caller already loaded; it never
reads a file or an environment variable (a library does no I/O; the
demo default of cisp Q16 "file-mounted PEM, two-key overlap" is the
caller's). Bound: at most `MaxRingKeys` (16) keys; `Rotate` past it is
refused and counted (E-10).

### 2. Detached JWS (RFC 7515 App. F, RFC 7797): the `X-JWS-Signature` header

```go
// DetachedHeader is the protected header the helpers write and read.
type DetachedHeader struct{ Alg, KID string; IssuedAt time.Time; B64 bool; Crit []string }   // Alg "RS256", B64 false, Crit ["b64"]
func (r *KeyRing) SignDetached(payload []byte, now time.Time) (string, error)           // "<protected>..<signature>" on the active key
func SignDetached(k SigningKey, payload []byte, now time.Time) (string, error)         // the same with one key (tests, tools)
type DetachedConfig struct {
    Publishers   map[string]IssuerConfig  // publisher id -> its JWKS URL or static set; the allow-list
    MaxAge       time.Duration            // iat may be at most this old; default DefaultDetachedMaxAge = 5 * time.Minute (M26)
    MaxSkew      time.Duration            // iat ahead of now by at most this; default DefaultMaxSkew
    MaxHeaderBytes int                    // bound on the header value; default DefaultMaxTokenBytes
    MaxPayloadBytes int64                 // bound on the payload; default DefaultMaxDetachedPayloadBytes (16 MiB)
    // the JWKS cache knobs of Config: JWKSCacheTTL, MinRefreshInterval, MaxJWKSBytes, JWKSFetchTimeout, JWKSRefreshAhead, HTTPClient, Now
}
type Signature struct{ Publisher, KID string; IssuedAt time.Time }
type DetachedVerifier struct{...}
func NewDetachedVerifier(ctx context.Context, c DetachedConfig) (*DetachedVerifier, error)
func (v *DetachedVerifier) Verify(ctx context.Context, publisher, header string, payload []byte) (Signature, error)
func (v *DetachedVerifier) Counters() *core.Counters
func ParseDetachedHeader(header string) (DetachedHeader, error)   // without verifying; for logging and for choosing the publisher by kid when the caller must
```

Wire form: `X-JWS-Signature: <BASE64URL(protected)>..<BASE64URL(sig)>`,
the payload being the exact request body bytes. The protected header is
`{"alg":"RS256","kid":"...","iat":<seconds>,"b64":false,"crit":["b64"]}`
and nothing else is required; unknown header members are tolerated,
unknown `crit` entries are refused (RFC 7515 §4.1.11). The signing input
is `ASCII(BASE64URL(protected)) || '.' || payload` (RFC 7797 §3, the
payload unencoded). `Verify` refuses, each with its counter and a
`*TokenError` whose `Claim` names the part: not two dots or an empty
middle part (`rejected_malformed`, claim `header`); a non-empty middle
part, which would be an attached payload (`rejected_malformed`); `alg`
not `RS256` (`rejected_algorithm`; `none`, HS*, PS*, ES* all refused);
`b64` absent or `true`, or `crit` missing `b64` (`rejected_b64`): the
header must declare the unencoded form, so a signature made over a
base64 payload never verifies against raw bytes; an unknown `crit`
member (`rejected_crit`); `kid` absent or not in the publisher's JWKS
(`rejected_kid`, with the same rate-limited refresh as `Verifier`);
publisher not in the allow-list (`rejected_publisher`, before any
network call); signature invalid (`rejected_signature`); `iat` absent,
older than `MaxAge` or ahead by more than `MaxSkew` (`rejected_iat`);
header or payload past its bound (`rejected_too_large`). Accepted
signatures count `accepted`.

The publisher is chosen by the caller from the bearer token it already
verified (`sub` = client id -> publisher), never from the header: a key
of publisher B can then never sign a publication attributed to A, and
`kid` collisions across publishers are harmless. `ParseDetachedHeader`
exists for logging and for a receiver that has no bearer (the webhook
case uses the compact form instead).

Implementation: `jws.Sign(nil, jws.WithKey(jwa.RS256(), priv),
jws.WithDetachedPayload(payload), jws.WithProtectedHeaders(hdr))` with
`b64` set to false in `hdr`, and `jws.Verify([]byte(header),
jws.WithKey(jwa.RS256(), pub), jws.WithDetachedPayload(payload),
jws.WithCritExtension("b64"))`. Pin the wire form independently of the
library (E-03): one test builds the signing input by hand from the RFC
text, signs it with `crypto/rsa` + `crypto/sha256` (`rsa.SignPKCS1v15`)
and checks that `SignDetached` produces the same signature for the same
key, header bytes and payload, and that `Verify` accepts the hand-built
value. One test uses the RFC 7797 §4.2 example (`b64:false`, `crit`,
detached, HS256 in the RFC) only to pin the header encoding and the
signing-input construction, since the key type differs. A payload
containing `.` must sign and verify (RFC 7797 §5.2 forbids it only for
the attached compact form; detached is fine).

### 3. Compact JWS: the webhook and direct-delivery form (M19, cisp Q9)

```go
type CompactClaims struct{ Issuer, Audience, Subject, JTI string; IssuedAt time.Time }    // iss, aud, sub, jti, iat
func (r *KeyRing) SignCompact(cl CompactClaims, body json.RawMessage, now time.Time) (string, error)   // active key; payload {"iss","aud","sub","iat","jti","body": body}
func SignCompact(k SigningKey, cl CompactClaims, body json.RawMessage, now time.Time) (string, error)
type CompactConfig struct {
    Issuers   map[string]IssuerConfig   // iss -> JWKS (the CISP and the ANSP, M5)
    Audiences []string                  // this receiver's hosts; aud must contain one (M18)
    MaxAge, MaxSkew time.Duration       // iat bounds; defaults as detached
    MaxTokenBytes int                   // default DefaultMaxTokenBytes
    // the JWKS cache knobs as above
}
type CompactVerifier struct{...}
func NewCompactVerifier(ctx context.Context, c CompactConfig) (*CompactVerifier, error)
func (v *CompactVerifier) Verify(ctx context.Context, token string) (CompactClaims, json.RawMessage, error)   // the verified claims and the body, untouched bytes
func (v *CompactVerifier) Counters() *core.Counters
```

The payload is a JSON object whose top level carries the five claims and
a `body` member holding the message (`cis/change/v1`) as the producer
wrote it. That makes the delivery a JWT (RFC 7519) with one private
claim, so the content type is `application/jose` and any JWT tool reads
the claims; the body is returned as raw bytes so the receiver validates
it against the CISP's schema itself. Header `alg RS256`, `kid`, and
`typ: "JWT"`. Refusals mirror `Verifier` (issuer not allow-listed
before any fetch, algorithm, kid, signature, `aud` not containing one
of `Audiences`, `iat` out of bounds, `jti` or `sub` empty, token past
its bound), each with its counter. There is no `exp`: a delivery is
single use and `jti` is the delivery id; the receiver's own idempotent
store is the replay guard, so `CompactVerifier` keeps no nonce memory
(stated in `doc.go`; the receiver repos already plan a delivery table).
`Verify` never accepts the payload of a token whose signature failed,
and never returns a body for a refused token.

The payload shape above is the contract the CISP (API owner, M14) and
the ANSP (direct delivery, M5) produce. If the CISP's `WP-2` lands first
on its own `internal/jws` with another shape, the CISP's shape wins and
this brief's `SignCompact` follows it in the same pull request: ask
before the first commit of part 3 whether `uspace-cisp` `WP-2` has
merged, and read its wire test if it has.

### 4. Proposed beside C1, flagged for the coordinator (strike if unwanted)

Three additive edits to the existing verifier that M18 and M20 require
of every system and that no sibling can make without core. They are not
in reconciliation §3 C1 by name; they are listed here because every
`*_AUDIENCES` plan edit of reconciliation §5 assumes a verifier that
takes a list.

- `Config.Audiences []string`: `aud` must contain any one of
  `Audiences` or `Audience`. With `Audiences` empty, behaviour is exactly
  `v1.0.0`'s; `jwt_verify.json` runs with `Audience` set as today.
  `Claims.Audience` reports the matched value.
- `Claims.Roles []string` (from a JSON array of strings `roles`) and
  `Claims.Realm string` (from `realm`): read when present, nil and empty
  when absent, never required (M20 session tokens are verified by the
  same verifier with `scope = "session"`). A `roles` value that is not an
  array of strings is `rejected_claims`, as any malformed claim is today.
- `NewVerifier` accepts `Audiences` with `Audience` empty.

Each is a new optional field; a `v1.0.0` caller compiles and behaves the
same. If the coordinator strikes them, note in the PR what the systems
are left with: the verifier refuses a wrong `aud` before the caller sees
any claim, so a system that must accept two hosts needs one `Verifier`
per audience and a first-match loop, and `roles`/`realm` are read from
the unverified payload after `Verify` accepted the token.

  and `Verifier` requires one, so the two do not share cases.

## Tests

- E-01 twins for every refusal above, each beside the accepted value
  that differs in exactly one thing (one byte of payload, one header
  member, `iat` one second past the bound either way, the retired key
  accepted and an unknown `kid` refused, publisher A's key under
  publisher B refused).
- E-02: a retired key keeps verifying after `Rotate`; a JWKS refresh
  failure keeps the cached publisher set (reuse the `jwksServer` of
  `jwt_test.go`); the accepted path's `Signature`/`CompactClaims` are
  read and checked field by field.
- E-03: the hand-built RSA signature test of part 2; a test that
  decodes the protected header of `SignDetached` output and checks
  exactly `alg`, `kid`, `iat`, `b64`, `crit` and nothing more.
- E-10: header, payload and token bounds exceeded; `MaxRingKeys`
  exceeded.
- E-11: `-race -shuffle=on`; `KeyRing.Rotate` concurrent with
  `SignDetached` and `JWKS`.
- Interop in both directions: a value signed by `SignDetached` verifies
  under `jws.Verify` called directly with the publisher's public key and
  `WithDetachedPayload`; a value signed by `jws.Sign` directly verifies
  under `DetachedVerifier`.
- `FuzzVerifyDetached(header string, payload []byte)` and
  `FuzzVerifyCompact(token string)`: no panic, no allocation past the
  bounds; seeded with the accepted values and every refusal.
- Benchmarks `BenchmarkSignDetached`, `BenchmarkVerifyDetached`,
  `BenchmarkVerifyCompact`, added to `docs/bench-targets.txt` at the
  `BenchmarkVerifyJWT` budget (200 000 ns/op: RSA dominates; plan §8.6).
- The unchanged proof: `make vectors` output pasted, 682/682, and
  `go test ./auth -run 'TestVectors'` green with no test edited.
